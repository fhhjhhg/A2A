## 2024-05-18 - [Optimize text streaming in Jupyter Notebook loops]
**Learning:** In Python, specifically in Jupyter Notebook loops that accumulate text for streaming outputs (`generate_text(..., stream=True)`), using `accumulated_content += new_chunk` paired with `clear_output(wait=True)` and `display(Markdown(accumulated_content))` does not eliminate O(N^2) complexity because `display()` and `clear_output()` act on the *entire* accumulated string on every iteration. However, refactoring to list accumulation (`accumulated_content.append(new_chunk)`) and `"".join()` inside the loop *still* copies the entire string for display, yielding zero measurable performance impact unless display updates are throttled.
**Action:** When refactoring text streaming loops in Jupyter Notebooks to avoid O(N^2) display overhead, list accumulation alone is insufficient. If optimization is strictly required, throttle the `display()` calls (e.g., updating every N chunks or using time-based throttling), or rely on CPython's in-place `+=` string optimization if throttling isn't feasible. In this codebase, preserving the `+=` loop is preferred over micro-optimizations that don't reduce display-bound overhead.

## 2024-05-18 - [Avoid RuntimeError for large float32 tensors with torch.quantile]
**Learning:** When calculating quantiles on large tensors (e.g., full MRI volumes > 16 million elements), `torch.quantile` may throw a `RuntimeError` due to size limitations for `float32` tensors. Furthermore, `np.percentile` expects a range of [0, 100] while `torch.quantile` uses [0.0, 1.0], and `np.percentile` returns a `float64` scalar which silently promotes the entire array to `float64` upon division, doubling memory consumption and causing downstream PyTorch runtime errors.
**Action:** Use `np.percentile` on NumPy arrays instead to handle these larger data structures efficiently. Always explicitly cast the result to a standard Python `float` (e.g., `float(np.percentile(..., percentile * 100))`) to avoid memory bloat and runtime errors.
